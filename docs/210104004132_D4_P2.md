## Session 8 — Web Experiment E1: EBNF Generation (Claude.ai Web)

**Late-execution acknowledgment.** Experiment E1 was required for the Part 1 D4 journal (submitted earlier this term) but was omitted from my submission by oversight. I noticed the gap on 2026-05-21 during a Part 2 D4 prep pass and am running E1 here, honestly dated, as a catch-up entry filed with my Part 2 D4 submission. This entry does **not** retroactively satisfy the Part 1 requirement; it documents the experiment for completeness and is also noted in my D5 retrospective. The model used (Claude Opus 4.7) postdates Part 1's working window, which is another reason to be explicit about when this was run rather than smuggle it into earlier dates.

Source session: [claude.ai/share/6d67cab6-006e-414f-b05c-ada5fa5b0d22](https://claude.ai/share/6d67cab6-006e-414f-b05c-ada5fa5b0d22). Two-turn session: cold EBNF generation, then comparison against the locked spec.

### Entry # 17 of 22 • Date 2026-05-21 • Phase Design / EBNF retrospective • AI tool Claude Opus 4.7 (extended thinking: on)

**Goal.** Generate a first-pass EBNF grammar for Recipix from a short prose description and compare it against my locked spec (v4.1, §13), so I can see which language-specific decisions an AI derives on its own and which it silently smooths over into PL-textbook defaults.

**Prompt.** *(verbatim, one paragraph, no productions or repository content leaked into turn 1; only the one-paragraph description below)*

> Recipix is a small domain-specific language for writing parameterized recipes that can be scaled and have ingredients substituted. The primitive types are `int`, `float`, `bool`, five quantity types (`Mass`, `Volume`, `Count`, `Temperature`, `Duration`), and a separate `Pinch` type. The structured types are `Ingredient`, `Recipe`, `Step`, and `List`. User-visible constructs are: recipe declarations with parameters and a `serves` clause; function declarations (`-> ReturnType`); ingredient declarations; step declarations with optional temperature and duration modifiers written with `at` and `for`; `let` bindings; `if`/`else`; `repeat N times`; `foreach x in list`; ordinary function and recipe calls; and three call-site-only operators: `evaluate <recipe>`, `scale(r, by: k)`, and `substitute(r, x, with: y, ratio: k)`. Quantity literals look like `200 g`, `1.5 kg`, `180 °C`, and `1 pinch`. There is a unary `quantity_of` operator that projects an `Ingredient` to its `Quantity`. Operator precedence should be standard (arithmetic, then comparison, then logical), and the chained-comparison case (`a < b < c`) should not be ambiguous. Please give me an EBNF grammar.

**Response (key part — turn 1, AI's first-pass EBNF generated cold).** Highlights from the AI's response, with the precedence ladder and the four spec-specific design choices verbatim:

```ebnf
(* Expression ladder — lowest to highest precedence *)
Expression     ::= LogicalOr
LogicalOr      ::= LogicalAnd ( "or"  LogicalAnd )*
LogicalAnd     ::= Comparison ( "and" Comparison )*
(* Non-associative on purpose — see notes on `a < b < c`. *)
Comparison     ::= Additive ( CompOp Additive )?
CompOp         ::= "<" | "<=" | ">" | ">=" | "==" | "!="
Additive       ::= Multiplicative ( ( "+" | "-" ) Multiplicative )*
Multiplicative ::= Unary ( ( "*" | "/" | "%" ) Unary )*
Unary          ::= ( "-" | "not" | "quantity_of" | "evaluate" ) Unary
                 | Postfix

SubstituteExpr ::= "substitute" "(" Expression "," Expression ","
                                   "with"  ":" Expression ","
                                   "ratio" ":" Expression ")"

QuantityLit    ::= ( INT_LIT | FLOAT_LIT ) Unit
```

The AI volunteered the following commentary on each spec corner I had asked it to be explicit about:

- **Quantity literals:** *"two tokens, joined in the parser. The lexer emits INT_LIT/FLOAT_LIT and a separate Unit token, and QuantityLit glues them at the parser level. Treating 200 g as a single lexer token would force the lexer to keep the full unit set and would be brittle if you ever want user-defined units."*
- **Chained comparison:** *"forbidden by making Comparison non-associative. The production is `Additive ( CompOp Additive )?` — at most one comparison operator."* Explicitly rejected the desugaring alternative.
- **`if`/`else`:** *"no dangling-else problem because bodies are braced. Because both branches must be { ... }, the classic ambiguity never arises."*
- **`quantity_of`:** *"sits at the unary layer, alongside -, not, and evaluate. So quantity_of flour + 100 g parses as (quantity_of flour) + 100 g."* Operand was parenthesis-free, not the locked `quantity_of(<expr>)` form.

The AI flagged its own uncertainty about `Count` ("I left it without a dedicated unit on the assumption it's promoted from INT_LIT by context") and named that as the most likely divergence from my spec before seeing it.

**Response (key part — turn 2, comparison against the locked spec).** I gave the AI the GitHub link to `docs/recipix_v4_1_spec.md` (§1, §5, §7, §8, §9, §13). Its summary:

> *"I got the high-stakes structural calls right — two-token quantities, non-associative comparison, mandatory if/else braces, quantity_of at the unary level — but missed the substitute bare-identifier restriction, and several smaller surface details I'll list at the end."*

Per-decision verdict:

| Decision | AI cold | Locked spec | Verdict |
|---|---|---|---|
| #7 quantity literals as two tokens | two tokens, parser-joined | two tokens, spec is sharper ("whitespace and `//` only between number and unit") | **match** (but AI missed `count`, had `°F`/`s`/`h` instead of `min`/`hr`, omitted `mg`) |
| #17 comparison non-associative | non-associative | non-associative, split `<rel_expr>`/`<eq_expr>` | **match**, same reasoning |
| #20 mandatory braces on if/else | mandatory, `else if` chain inline | mandatory, `else if` via nested if | **match** |
| #34 `quantity_of` at unary level | unary level, operand without parens | unary level, operand with parens | "right floor, wrong storefront" — match on placement, miss on surface syntax |
| #35 substitute slots as bare IDENT | all four slots `Expression` | ingredient slots are `IDENT` terminals | **miss** — the one big design call the AI invented from prose was wrong |

The AI's own framing of the substitute miss:

> *"Your AST node carries original_name: str and replacement_name: str, not Expr — there is no AST shape that pretends the slot could be computed. That's a cleaner separation than what mine produced. I'd treat this as the cleanest design lesson in the whole comparison — grammar-as-documentation-of-semantics, not just grammar-as-parser-spec."*

**Accepted.** The four high-stakes calls match the locked grammar's intent, and the AI's reasoning on each (lexer simplicity for two-token quantities, parse-time error rather than type-time error for non-associative comparison, dangling-else-by-construction for mandatory braces, no-`FunctionType`-can-express-this for `quantity_of` at unary) lines up with the rationale I locked into the spec and the v4.1 decision table. Precedence-ladder shape (seven levels in the right top-down order) and program skeleton both match. Even the "right floor, wrong storefront" miss on `quantity_of` proves the type-system reasoning was sound; only the surface syntax differed.

**Rejected / modified.** The one decision-level miss (substitute slots) and a cluster of over-permits, in the AI's own self-categorization:

1. **`substitute` slots as `Expression` instead of `IDENT`.** Real miss. Under the AI's grammar, `substitute(r, flour + salt, with: milk, ratio: 1.0)` parses; under the spec, it's a parse error. Decision #28 rationale (ingredient identity *is* the symbol-table binding, not the `name` field's contents) is invisible in the AI's grammar and visible in mine.
2. **`let` type annotation made optional.** Spec §7 requires it in v1.
3. **`List<T>` as a user-writable type annotation.** Decision #32 explicitly forbids that in v1; lists are inferred.
4. **Top-level `IngredientDecl`.** Spec §6 scopes ingredient names to the enclosing recipe.
5. **Step body absent entirely.** AI's `StepDecl ::= "step" Expression StepModifier*` had no `{ ... }` action block, described description as general `Expression` rather than `STRING_LIT`.
6. **Action verbs not anticipated.** No closed reserved set, no Decision #29 carve-out.
7. **Recipe calls labelled-argument style.** Spec samples use `pancakes(servings: 4)`; AI's grammar is positional-only.
8. **Function body too permissive.** Spec §7 forbids early return; AI had a general `Block`.
9. **Postfix indexing `e[i]`.** Spec has no user-facing list indexing.
10. **Logical operator surface forms.** AI used keyword spellings (`and`, `or`, `not`); spec §1 uses symbol spellings (`&&`, `||`, `!`).
11. **Unit set wrong in three places.** Missing `count` (AI flagged this itself), missing `mg`, spurious `°F`/`s`/`h` instead of locked `min`/`hr`.

**Errors caught.** Consolidated to the consequences I'd defend on the exam:

1. **`substitute` slots as `Expression` (decision #35) — wrong.** Under the AI grammar, an arbitrary expression can compute "which ingredient to substitute," defeating decision #28. The AI's retrospective named this as the cleanest design lesson; I keep it as the strongest exam-quote line from the session.
2. **Cluster of over-permits where the spec locks down** (decisions #32, §6 scoping, §7 single-return). The AI admits whatever generic PL languages admit; the spec restricts what Recipix specifically restricts. This is the predictable shape of "derive a grammar from prose without the locked decisions in view."
3. **`quantity_of` as parens-free prefix instead of `quantity_of(<expr>)` (decision #34).** Surface miss only; type-system reasoning was correct. The locked parens form is intentionally call-looking to read naturally while the grammar production keeps it from actually being a function.
4. **Unit set drift.** AI invented units (`°F`, `s`, `h`) and missed locked ones (`count`, `mg`). Any program written against the AI grammar with `30 s` or `200 °F` lexes/parses fine under that grammar then dies against my actual lexer.

**Reflection.** The thing that surprised me here is how much Opus got right cold with thinking on. Four of five big design calls came back match — quantity literals as two tokens, non-associative comparison, mandatory braces, `quantity_of` at the unary level. I'd expected closer to zero. What didn't change is the kind of thing it still misses. Decision #28 ("ingredient identity is the binding") drives Decision #35 (substitute slots are bare identifiers), and there's no way to derive #35 from prose unless you've already had the #28 conversation. The over-permits — `List<T>` annotations as user-writable, top-level ingredients, optional `let` type, indexing, multi-return function bodies — are the same shape: the AI admits whatever generic PL languages admit; the spec restricts what Recipix specifically restricts. Lesson: I can't trust a "generate a grammar from a paragraph" pass to surface decisions whose rationale lives outside that paragraph. I have to drive the AI with the rationale already in hand. That's also why I'm filing this entry on its real date and not backdated — the value of the experiment is in the comparison, and the comparison only holds if the dates and tool name are honest.

## Session 9 — Web Experiment E2: Type Equivalence (Claude.ai Web)

Source session: [claude.ai/share/dd9a44cf-584d-4194-9312-2b512752f90d](https://claude.ai/share/dd9a44cf-584d-4194-9312-2b512752f90d). Two-turn session: cold equivalence recommendation, then comparison against the locked spec.

### Entry # 18 of 22 • Date 2026-05-21 • Phase Type checker / Design • AI tool Claude Opus 4.7 (extended thinking: on)

**Goal.** Test whether a fresh AI session, given only a one-paragraph description of Recipix and its structured types, can derive the type-equivalence rule I actually settled on in v4.1 — or whether it gives a textbook answer that misses the domain reason for the split.

**Prompt.** *(verbatim — Recipix domain framing + the four structured types, asking for a per-type name-vs-structural recommendation + a small example program that depends on the rule)*

> I'm working on Recipix, a small DSL for parameterized recipes... Here are Recipix's structured types:
> - `Ingredient { name, quantity }`
> - `Recipe { name, servings, ingredients, steps }`
> - `Step { description, temperature?, duration?, actions }`
> - `List<T>` (homogeneous; element type inferred at literal construction)
>
> Question, drawing on Sebesta §6.14: for each of these four structured types, should Recipix use **name equivalence** or **structural equivalence**? Justify each choice individually. Then write a small example Recipix program that depends on the rules you picked.

**Response (key part — turn 1, AI's first-pass recommendation).**

| Type | AI cold recommendation | AI's justification |
|---|---|---|
| **Ingredient** | name equivalence | *"It's a domain noun ... the fields {name, quantity} are generic enough that structural rules would collapse it with anything shaped the same way. If you ever add a Cost { name, quantity } for pricing or an Allergen { name, quantity } for labeling, structural equivalence makes them silently interchangeable."* |
| **Recipe** | name equivalence | *"Recipe is the top-level entity. Accidental equivalence at the top of the type lattice is a worse failure mode than at the leaves; you really don't want a metadata record shaped {name, servings, ingredients, steps} to typecheck as a Recipe because someone happened to pick those field names."* |
| **Step** | name equivalence | *"The two ? make it decisive. Under structural rules, {description, actions}, {description, temperature, actions}, {description, duration, actions}, and {description, temperature, duration, actions} are four distinct types. A homogeneous List<Step> couldn't hold a mix, which defeats the entire point of optional fields."* |
| **List\<T\>** | structural in parameter, nominal in constructor | *"`List` is the same named constructor everywhere; whether two List<T> instantiations are equivalent reduces to whether their Ts are equivalent under whatever rule applies to T."* |

The AI offered a brownies-recipe example using pseudo-syntax (`Step("desc", actions: [...])` constructor calls inside a `steps: [...]` list literal). The load-bearing claim was that under structural Step equivalence, the three step values — one with neither modifier, one with both, one with only `duration` — would have three distinct structural shapes and fail to unify in a `List<Step>`.

**Response (key part — turn 2, comparison against the locked spec).** I gave the AI the GitHub link to `docs/recipix_v4_1_spec.md` §2 and decision #10. Its self-assessment:

1. **Recipe — match.** Same call, same reasoning.
2. **List\<T\> — match.** Same conceptual move, phrased differently.
3. **Ingredient — divergence, with self-correction.** The AI's retrospective:
   > *"My reasoning was forward-looking: avoid silent collisions with hypothetical Cost { name, quantity } or Allergen { name, quantity } types in some v2. That argument falls apart against your actual v1, because there is no user-defined record syntax — Ingredient is the only {name, quantity} record the type system will ever see, and §1 makes the type-name set closed. So my choice was buying safety against a threat that can't exist in the language as specified. In v1 the two rules are observationally equivalent, but yours is the cleaner architectural call for a sealed language: pick the more permissive rule when over-restriction has no upside."*
4. **Step — divergence on reasoning.** The AI realized its argument was based on the strict-Sebesta reading of structural equivalence (each `?`-field present-or-absent creates a distinct shape) — *not* how the spec applies the rule. The spec treats optional fields as part of the *single* declared shape. The AI's retrospective:
   > *"temperature? and duration? are declared as optional members of the single Step shape. A Step value with duration filled and one with neither both inhabit that single declared shape. The structural rule unifies them. The list type-checks. The example runs."*

The AI also flagged a separate problem with its own example:
   > *"my brownies program used pseudo-syntax. That's not actual Recipix surface syntax — steps are introduced by step declarations inside a recipe body. In the real syntax there isn't even a user-visible List<Step> for the equivalence rule to apply to."*

The AI's one-line summary:
   > *"I got Ingredient genuinely wrong (defensible reasoning, wrong call for a sealed v1), I got Step nominally wrong but on a question your spec doesn't actually need to answer, and my example was sold as a discriminating test case when it isn't one under your rules."*

**Accepted.** Recipe and List\<T\> calls match the spec's intent. The reasoning the AI gave for Recipe ("accidental equivalence at the top of the type lattice prevents accidental shape-matches with hypothetical metadata records") is essentially the defense the spec gives for decision #10. The List\<T\> move (equivalence on `List<T>` reduces to equivalence on `T`) is right and the AI cites ML / Haskell / Java-generics as precedent unprompted. AI's framing in turn 2 — *"pick the more permissive rule when over-restriction has no upside"* — is a one-liner defense of decision #10's structural-for-Ingredient call that I can quote almost verbatim in D1 §4.8.

**Rejected / modified.** Three substantive divergences:

1. **Ingredient: AI picked name, spec picks structural.** The AI's defense was forward-looking (hypothetical `Cost` / `Allergen` records). v1 has no user-defined records, so the threat can't exist; structural is the more permissive rule that doesn't pay a cost. The AI's own retrospective recognized this without me arguing it.
2. **Step: AI's reasoning relied on the strict-Sebesta reading of structural equivalence.** The AI assumed each present/absent combination of optional fields produced a distinct shape (4 shapes for 2 optionals). The spec treats optional fields as part of the single declared shape. The locked spec is silent on whether to call this "name" or "structural" because, as the AI's retrospective noted, *Step values never appear in positions where the rule is observable in v1.* Steps are introduced by `step` declarations inside a recipe body, never assembled into a user-visible `List<Step>`.
3. **Pseudo-syntax in the example.** The brownies program uses constructor-call syntax for ingredients and steps and a `steps: [...]` list literal. That's not Recipix surface syntax.

**Errors caught.** Three findings I'd defend on the exam:

1. **AI's domain reasoning optimized for extensibility scenarios that the closed v1 type-name set forecloses.** Its choice of name equivalence for Ingredient was correct *given* an open record-type system; wrong *given* Recipix's sealed v1. AI design reasoning tends to imagine the language is extensible by default; the spec's job is to know what it has actually committed to.
2. **AI assumed a stricter notion of structural equivalence than the spec uses.** Sebesta §6.14 frames structural equivalence as field-set match; the spec extends that to "declared shape including optionals." This is a real design move and the AI failed to credit it.
3. **The example program does not run under the rule it claimed to demonstrate.** This is the literal test the handout's E2 specification names: *"Does the example it gives actually run under the equivalence rule it described?"* The answer is no — under the spec's structural rule the example's three step values unify fine, so the example doesn't discriminate between name and structural equivalence. The example also uses pseudo-syntax that wouldn't parse.

**Reflection.** The interesting result here isn't that the AI got Ingredient wrong — it's that the reasoning behind the wrong answer was sophisticated and forward-looking, and would have been correct for a different language. It hedged against `Cost { name, quantity }` collisions that v1 makes impossible because the type-name set is closed. That's the failure mode I think I'll see most often when prompting AI on Recipix design questions: the AI optimizes for the kind of evolution a generic record-based DSL would undergo, and v1 has already foreclosed those evolutions. The Step finding has the same shape — the AI read §6.14's structural rule strictly ("match the field set position-for-position"); the spec read it permissively ("match the declared shape, optionals included"). Both moves are the AI defaulting to the strictest reading of a textbook concept when the spec deliberately picked a looser one. Lesson for §4.8 and the rest of D4: the AI accelerates generating design options. It does not decide which option a sealed v1 has already committed to. That's mine.

## Session 10 — Web Experiment E3: AI Implements `_check_ActionStmt` (Claude.ai Web)

Source session: [claude.ai/share/8190d922-7330-4181-84cd-40e1748c1e99](https://claude.ai/share/8190d922-7330-4181-84cd-40e1748c1e99). Two-turn session: cold implementation, then comparison against plan §2.3 and the typechecker stub.

### Entry # 19 of 22 • Date 2026-05-21 • Phase Type checker • AI tool Claude Opus 4.7 (extended thinking: on)

**Goal.** Have the AI implement `_check_ActionStmt` on the `TypeChecker` class — the §10 error-#13 enforcer for the twelve closed verbs in spec §8 — without first showing it the three-class table from plan §2.3, then compare its inferred signatures to the locked design.

**Prompt.** *(verbatim — the twelve verbs, the type-string contract for `env.lookup`, the four test inputs whose right answers I knew in advance)*

> Recipix has a closed set of twelve action verbs (spec §8): combine, mix, add, sprinkle, pour, drizzle, whisk, blend, knead, melt, bake, flip. Values are Ingredient<D>, Quantity<D>, and Pinch where D ∈ {Mass, Volume, Count, Temperature, Duration}. Per plan §2.3 the verbs fall into three signature classes — infer or reconstruct the table from the verb semantics plus the spec's closed verb list; do not ask me to paste it. Implement `_check_ActionStmt(self, node)`... Use at least one helper data structure (a verb-signature dict/table).

The AI unsolicited-flagged an ambiguity in the very prompt before answering — *"you said D ∈ {Mass, Volume, Count, Temperature, Duration} — Pinch is not in D — but then the example return value mentions Quantity<Pinch>, and test #1 uses Ingredient<Pinch>. So either Pinch is a valid dimension or Ingredient<Pinch> shouldn't have made it past an earlier check."* Real prompt bug; the spec treats Pinch as a primitive, not a dimension, but the implicit-projection rule (#31) and the test inputs effectively require the checker to handle `Ingredient<Pinch>` as well-formed. v4.2 spec wording needs to clarify.

**Response (key part — turn 1, AI's first-pass implementation).** The signature table (the design-significant payload) verbatim:

```python
VERB_SIGS = {
    'combine': ('variadic', [], _ingredient_of(), 2),
```

|---|---|---|---|---|
| 1 | combine(flour, salt) | accept | accept | match (right verdict, wrong rule) |

**Rejected / modified.** Everything in the cold first-pass except the dispatcher skeleton: the twelve-row `VERB_SIGS` table (replaced wholesale with the three-class form), per-verb dimension locks on pour/drizzle/knead/melt/sprinkle (no per-verb dim in spec, only homogeneity), combine/mix/blend min-arity ≥2 (spec is ≥1), bespoke `add` signature (heterogeneous-class default), bake as fixed arity 3 (spec lifts temperature/duration into `at`/`for` step modifiers, leaves bake nullary), flip as unary (nullary), whisk as unary (homogeneous), missing implicit Ingredient → Quantity projection (#31).

**Errors caught.** Five concrete findings I'd defend on the exam:

1. **Test 2 verdict flipped under §2.3.** AI rejected because of hard-coded Volume; spec accepts because pour is homogeneous and single-arg is trivially homogeneous. **The single best illustration of the per-verb-vs-per-class trade-off** — spec gives up English-language verb semantics ("pour" implying liquid) to buy type-system parsimony. Likely exam question: *"why does pour(flour) type-check in your language?"* Answer: *"because §2.3 deliberately chose the looser rule; per-verb dimensions are a backwards-compatible v2 refinement candidate."*
2. **Test 4 verdict flipped under §2.3.** AI grouped blend with combine/mix as heterogeneous; spec puts it in homogeneous (Volume + Mass mismatch). Spec uses physical-coherence as the homogeneity argument, not literal "blender = liquid" cooking sense.
3. **Test 3 matched for the wrong reason.** AI rejected for arity 3≠1; spec rejects for arity 0≠1. Accept/reject column matches by coincidence; reasoning matches doesn't.
4. **Decision #31 (Ingredient → Quantity projection) absent.** AI predicates couldn't handle Ingredient appearing in a position that expects a Quantity. Under #31, the homogeneous class projects through automatically. Not surfaced by the four test inputs but would surface in real programs.
5. **Per-verb cooking-semantics signatures over-specify against spec's type-system parsimony.** Structural finding from AI's self-critique: *"I optimized for cooking semantics; you optimized for type-system parsimony."* This is the single most defensible journal-quote line from the session.

**Reflection.** The biggest takeaway from this one is that the AI's design instinct — "more rules cover more cases" — is exactly opposite to the spec's instinct of "fewer rules cover the same cases at lower exam and maintenance cost." Twelve per-verb signatures look like authority on first read; the AI's own retrospective lands on this in one line: *"I optimized for cooking semantics; you optimized for type-system parsimony."* That framing is the one I want in §4.8 and in my head for the oral. The per-verb cooking-semantics signatures aren't wrong because the cooking semantics are wrong — they're wrong because pricing language-design decisions in cooking-intuition currency means the action-verb checker has twelve places it can break instead of three. The spec's three-class collapse trades verb-meaning-faithfulness for fewer-places-to-be-wrong. The thing the journal needs to show is that the AI's cold-reasoning instinct went the other way. The other half of the experiment is what happened after the spec came into view: the AI wrote its own §2.3-aligned correction, unsolicited, and got it essentially right. AI implements decisions well. It does not invent them well. That's the working pattern I'll keep across the rest of Part 2 — I drive the decisions, the AI drives the implementation, and the journal is the record of what happens when those roles slip.
