1. Language Overview

Recipix is a statically-typed domain-specific programming language for describing, parameterizing, scaling, and substituting recipes. It targets home cooks and food developers who want machine-checkable recipes: no more "double the recipe and hope the baking temperature is also doubled" errors.

Core design values (Sebesta Ch. 1 evaluation criteria):

  • Readability — ingredient declarations look like natural-language recipes; action verbs (combine, bake, blend) are reserved keywords that mirror kitchen vocabulary.
  • Writability — common patterns (scaling servings, substituting one ingredient) are first-class operations, not library calls. Implicit Ingredient→Quantity projection removes boilerplate in arithmetic.
  • Reliability — dimensional type system catches mismatches at compile time. Adding grams to millilitres is a type error, not a runtime surprise.
  • Cost — no runtime until the programmer writes evaluate; parse errors are caught early and reported with line numbers.

What makes Recipix a DSL, not a general-purpose language: Every numeric quantity carries a physical dimension (Mass, Volume, Count, Temperature, Duration). The type system enforces dimensional correctness at compile time. A general-purpose language treats 200 and 500 as raw numbers and allows nonsensical combinations; Recipix makes such combinations impossible to express.

2. Lexical Structure

Sebesta §3.1–3.2 — Lexical analysis, token categories

2.1 Basic Rules

  • Whitespace (spaces, tabs, newlines) separates tokens. Comments begin with // and run to end-of-line.
  • Identifiers match [a-zA-Z_][a-zA-Z0-9_]*. Case-sensitive. ASCII only.
  • String literals: "...", UTF-8 content, any character except " and newline. No escape sequences in v1.
  • Integer literals: decimal digits only. Float literals: decimal with mandatory digits on both sides of the dot.

2.2 Token Categories

2.3 Decision #7 — Two-Token Quantity Literals

Choice: A quantity is two tokens: a numeric literal (INT_LIT or FLOAT_LIT) followed by a UNIT_KW. Whitespace and // comments may separate them; no other tokens may appear between them. The parser combines the pair into a QuantityLit AST node.
Rationale: Single-token quantities like 200g create lexer ambiguity (is g a unit or an identifier prefix?). Two tokens eliminate ambiguity at the lexical level with no lookahead cost. (Sebesta §4.2 — token forms and maximal munch)
Trade-off: Constructing a quantity from a computed value requires expr * 1 unit syntax, slightly more verbose. 
200 g       → INT_LIT(200)   UNIT_KW('g')
1.5 kg      → FLOAT_LIT(1.5) UNIT_KW('kg')
180 °C      → INT_LIT(180)   UNIT_KW('°C')
200g        → LexerError: Missing separator (decision #7)

2.4 The °C Token

The degree-Celsius unit is a single UNIT_KW token with value '°C'. The degree symbol (U+00B0) cannot appear standalone. This was implemented with a dedicated scanner method _scan_degree_c() that consumes ° then requires C to follow immediately.

2.5 Keyword Disambiguation (Maximal Munch)

When a word is scanned, classification priority is: true/false → BOOL_LIT; unit keywords → UNIT_KW; type keywords → TYPE_KW; action verbs → ACTION_KW; reserved words → token type = keyword text; else → IDENT. This matches Sebesta §3.2's recommendation for keyword pre-emption in hand-written lexers.

3. Grammar (EBNF)

Sebesta §3.3 — BNF/EBNF grammars

Full grammar in EBNF notation. [ ] = optional, { } = zero or more, ( | ) = alternatives.

<program>      ::= { <top_decl> } EOF
<top_decl>     ::= <recipe_decl>
                 |  <function_decl>
                 |  <eval_stmt>

<recipe_decl>  ::= "recipe" IDENT "(" [ <param_list> ] ")" "serves" <expr> "{"
                       { <ingredient_decl> }
                       { <step_decl> }
                   "}"

<function_decl> ::= "function" IDENT "(" [ <param_list> ] ")" "->" TYPE_KW "{"
                        { <stmt> }
                        "return" <expr>
                    "}"

<param_list>   ::= <param> { "," <param> }
<param>        ::= IDENT ":" TYPE_KW

<ingredient_decl> ::= "ingredient" IDENT ":" <expr>

<step_decl>    ::= "step" STRING_LIT [ "at" <expr> ] [ "for" <expr> ] "{"
                       { <stmt> }
                   "}"

<eval_stmt>    ::= "evaluate" <expr>

<stmt>         ::= <let_stmt>
                 |  <if_stmt>
                 |  <repeat_stmt>
                 |  <foreach_stmt>
                 |  <return_stmt>
                 |  <action_stmt>
                 |  <expr_stmt>

<let_stmt>     ::= "let" IDENT ":" TYPE_KW "=" <expr>
<if_stmt>      ::= "if" <expr> "{" { <stmt> } "}" [ "else" "{" { <stmt> } "}" ]
<repeat_stmt>  ::= "repeat" <expr> "times" "{" { <stmt> } "}"
<foreach_stmt> ::= "foreach" IDENT "in" <expr> "{" { <stmt> } "}"
<return_stmt>  ::= "return" <expr>
<action_stmt>  ::= ACTION_KW "(" [ <arg_list> ] ")"

<expr>         ::= <or_expr>
<or_expr>      ::= <and_expr> { "||" <and_expr> }
<and_expr>     ::= <eq_expr> { "&&" <eq_expr> }
<eq_expr>      ::= <rel_expr> [ ( "==" | "!=" ) <rel_expr> ]
<rel_expr>     ::= <add_expr> [ ( "<" | "<=" | ">" | ">=" ) <add_expr> ]
<add_expr>     ::= <mul_expr> { ( "+" | "-" ) <mul_expr> }
<mul_expr>     ::= <unary> { ( "*" | "/" ) <unary> }
<unary>        ::= "-" <unary>
                 |  "!" <unary>
                 |  "quantity_of" "(" <expr> ")"
                 |  <primary>

<primary>      ::= INT_LIT [ UNIT_KW ]
                 |  FLOAT_LIT [ UNIT_KW ]
                 |  STRING_LIT
                 |  BOOL_LIT
                 |  "[" [ <expr> { "," <expr> } ] "]"
                 |  <call_expr>
                 |  IDENT
                 |  "(" <expr> ")"

<call_expr>    ::= <scale_call>
                 |  <substitute_call>
                 |  IDENT "(" <recipe_or_fn_args> ")"

<scale_call>       ::= "scale" "(" <expr> "," "by" ":" <expr> ")"
<substitute_call>  ::= "substitute" "(" <expr> "," IDENT "," "with" ":" IDENT "," "ratio" ":" <expr> ")"

<recipe_or_fn_args> ::= [ <kw_arg> { "," <kw_arg> } ]     (* keyword-arg: recipe call *)
                       | [ <expr> { "," <expr> } ]          (* positional: function call *)

<kw_arg>       ::= IDENT ":" <expr>
<arg_list>     ::= <expr> { "," <expr> }

Key grammar decisions encoded above:

  • #20 Mandatory braces on if/else — "{" ... "}" is required in both branches; eliminates dangling-else ambiguity (Sebesta §3.4, §8.1).
  • #23 Fixed modifier order — "at" appears before "for" in the step production; both are optional.
  • #17 Non-associative comparisons — <eq_expr> and <rel_expr> use [ ] (optional, once) not { } (repeating); chaining like a < b < c is a parse error.
  • #34 quantity_of as unary operator — appears in <unary>, never in <primary>; cannot be called as a function.
  • #35 substitute slots as bare IDENTs — the two ingredient slots in <substitute_call> are IDENT terminals, not <expr>.
  • #7 Quantity literals — INT_LIT [ UNIT_KW ] in <primary>; the optional unit is a lookahead, not part of a separate production.

4.3 Structured Types

  • Ingredient — record: name (label), quantity (Quantity<D> or Pinch). Structural equivalence.
  • Recipe — record: name, servings, ingredients, steps. Name equivalence (Decision #10).
  • List<T> — homogeneous list; element type inferred. No user-facing list type annotation in v1 (Decision #32).

4.4 Type Equivalence (Decision #10)

Structural for Quantity, Ingredient, List — any two Mass values are the same type, regardless of unit (g and kg are representations of the same dimension).
Name for Recipe — pancakes and crepes are different types even if they have the same ingredient set.
Rationale: units are convertible; recipe identity is not (Sebesta §6.14).

4.5 Implicit Projection: Ingredient → Quantity (Decision #31)

When an Ingredient appears in arithmetic or comparison context, it implicitly projects to its quantity field. The explicit form quantity_of(flour) is always available.

Trade-off: Minor loss of type-system uniformity; substantial readability gain — without it, every arithmetic expression inside a recipe would require an explicit projection.

5. Operator Precedence and Arithmetic

Sebesta §7.2, §7.4, §7.5, §7.6

LevelOperatorsAssociativity
1 (highest)unary -, !, quantity_of(...)Right
2*, /Left
3+, - (binary)Left
4<, <=, >, >=Non-associative (Decision #17)
5==, !=Non-associative
6&&Left
7 (lowest)||Left

Decision #17 — Non-associative comparisons: a < b < c is a parse error (not silently mis-parsed as (a < b) < c with a bool-to-int coercion, which would be a reliability hazard). Sebesta §7.2 discusses ambiguity in operator grammar.

Decision #18 — Operand evaluation order: Left-to-right, fully defined. No undefined behavior (Sebesta §7.6).

Decision #19 — Short-circuit evaluation: && and || short-circuit left-to-right (Sebesta §7.5).

6. Names, Binding, Scope, and Lifetime

Sebesta §5.2–5.5 — Names, binding, scoping

6.1 Identifier Rules

Identifiers match [a-zA-Z_][a-zA-Z0-9_]*, are case-sensitive, and must not collide with any keyword category (reserved, type, action, or unit).

6.2 Binding Times (Decision #13, #14)

Sebesta §5.4 — Binding and binding times

EntityType bound atValue bound at
Recipe / function declarationsCompile timeCompile time (static)
Ingredient typesCompile time—
Ingredient quantitiesCompile timeRuntime (recipe instantiation)
Recipe / function parametersCompile timeRuntime (call site)
let-bound namesCompile time (annotation required)Runtime (initializer)
Loop variables (foreach)Compile time (inferred)Runtime (each iteration)

Type annotation is mandatory on let declarations (no type inference in v1). This follows Sebesta's distinction between static and dynamic binding: type is a compile-time attribute, value is a runtime attribute.

6.3 Scoping (Decision #11, #12)

Static (lexical) scoping throughout — equivalent to Sebesta §5.5's static scope rule. Each of the following constructs opens a fresh scope:

  • A recipe body (parameters + ingredients in scope)
  • A function body (parameters in scope)
  • A step body (enclosing recipe's ingredients in scope)
  • Each if and else block (independently)
  • A repeat body
  • A foreach body (loop variable in scope)

Inner scopes can read outer-scope names. Shadowing is forbidden (Decision #12): re-declaring a name visible in any enclosing scope is a compile-time error. This prevents accidental variable hiding, improving reliability at the cost of slightly reduced flexibility.

6.4 Single-Assignment Discipline (Decision #13)

All bindings are immutable after their initializer runs: ingredient names, let-bound names, function/recipe parameters, and loop variables are each assigned exactly once. This is a deliberate choice for reliability — no mutation means no aliasing bugs.

6.5 Lifetime (Decision #14)

Sebesta §5.4.3 — Variable lifetime categories

EntityLifetime
Recipe and function declarationsStatic — whole program (Sebesta §5.4.3)
Recipe and function parametersStack-dynamic — per instantiation/call
Ingredients within a recipeStack-dynamic — per recipe instantiation
let-bound namesStack-dynamic — per enclosing scope
Loop variablesStack-dynamic — per iteration

6.6 Parameter Passing (Decision #16)

Semantically by-value for all types. Because Recipix has no mutation in v1, by-value and by-reference are indistinguishable at the language level. The implementation copies primitives and quantities; for recipes and lists it shares immutable references to avoid unnecessary copying — but programs cannot detect this because no operation modifies a referenced value.

If Recipix v2 introduces mutation, this decision would be the first thing to revisit. (Sebesta §9.5 — parameter-passing modes)

7. Domain-Specific Operations

Sebesta §9 — Subprograms and parameter passing

All three operations are call-site only: they cannot appear inside a recipe body.

7.1 evaluate

evaluate <recipe_expr>

Top-level only. Type-checks and elaborates the recipe expression into a final printable recipe value with all quantities normalized.

7.2 scale (Decision #25)

scale(<recipe_expr>, by: <scalar_expr>)

Returns a fresh Recipe value; does not mutate the original (referential transparency). Multiplies Mass, Volume, and Count quantities by the scalar; does not scale Temperature or Duration. Multiplies servings by the scalar (rounded to int).

7.3 substitute (Decision #35)

substitute(<recipe_expr>, <ingredient_name>, with: <ingredient_name>, ratio: <scalar_expr>)

Returns a fresh Recipe value. The two ingredient-name slots are bare identifiers (IDENT terminals in the grammar, str in the AST), not general expressions. They are resolved at compile time as symbol-table lookups in the recipe's ingredient table.

Rationale (Decision #28 + #35): Ingredient identity is the symbol-table binding, not a string match on the name field. Making the restriction visible in the grammar itself (IDENT, not expr) keeps the semantics honest: you are specifying a compile-time lookup, not a runtime value search.
