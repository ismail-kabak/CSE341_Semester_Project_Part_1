Entry #1 of 4  |  Date: 2026-05-04  |  Phase: Design  |  Tool: Claude Sonnet 4.6

Goal

Choose a DSL domain and decide on primitive and structured types, given that the assignment requires at least three primitives, one structured type, and a domain-specific construct.

Prompt (verbatim)

"I need to design a DSL for a programming languages course. The domain is recipe scaling and substitution — ingredients have physical units (grams, ml, °C). What primitive and structured types should I have, and how should I handle dimensional quantities? The language must have at least 3 primitives, 1 structured type, and a domain-specific construct."

Response (key part)

Claude suggested: primitives int, float, bool; domain primitives Mass, Volume, Temperature, Duration, Count as named quantity types; a Pinch type for ceremonial amounts with no arithmetic; and structured types Ingredient, Recipe, List<T>. It argued for a split type-equivalence rule: structural for quantities (since 200 g and 0.2 kg are the same mass), name for recipes (since pancakes and crepes should not be interchangeable).

Accepted

The Pinch type as a ceremonial primitive with no arithmetic — this was non-obvious and genuinely useful. The structural-vs-name equivalence split. The quantity type family (Mass, Volume, etc.) rather than a generic Quantity<D> in user syntax.

Rejected / modified

Claude initially suggested a generic Quantity<D> syntax in user programs. I rejected this because it requires angle-bracket type parameters which complicates the lexer and parser significantly. I locked the type names to a closed set of keywords instead (Decision #32).

Errors caught

Claude said "quantity comparisons should be allowed across dimensions if you normalize first." This is wrong — you cannot compare a temperature to a duration even after normalization. Caught by checking the physics: dimensions are not comparably ordered. We restricted comparisons to same-dimension only.

Reflection

AI is effective for enumerating design options but does not always apply domain constraints correctly. The temperature-vs-duration comparison error would have silently entered the type system if I had accepted it. The correct approach is to verify every rule against the actual domain semantics, not just syntactic consistency.

Entry #2 of 4  |  Date: 2026-05-05  |  Phase: Lexer  |  Tool: Claude Sonnet 4.6

Goal

Implement the hand-written lexer for Recipix, specifically handling the two-token quantity literal rule (Decision #7) and the °C multi-character unit token.

Prompt (verbatim)

"Write a hand-written lexer in Python for a DSL where quantities are two tokens: INT_LIT or FLOAT_LIT followed by UNIT_KW with mandatory whitespace between them. '200g' (no separator) must be a LexerError. Also '°C' must be a single UNIT_KW token — the degree symbol cannot appear alone. Use a Token dataclass with type, value, line fields."

Response (key part)

Claude produced a complete Lexer class with _scan_number(), _scan_string(), _scan_word(), _scan_degree_c(), and a _check_no_unit_glued() method that raised LexerError when an alphabetic character immediately followed a number.

Accepted

The overall structure (one method per token category), the maximal-munch two-character operator handling, the keyword pre-emption priority order (true/false → unit → type → action → reserved → IDENT), and the _scan_degree_c() implementation.

Rejected / modified

The _check_no_unit_glued() method checked nxt.isalpha() — any letter after a number triggered the error. This was too broad: 200foo would error even though foo is just an identifier. I rewrote it to scan ahead and only raise the error if the full word is in UNIT_KEYWORDS.

Errors caught

Bug: 200foo raised "Missing separator between number and unit" — but foo is not a unit. Detected by running the lexer on ingredient x : 200 followed by a variable name. Fixed by scanning ahead for the full word before checking UNIT_KEYWORDS.

Reflection

AI-generated code tends to over-generalize safety checks. The "check for any letter" heuristic looks defensive but is actually wrong — Decision #7 is specifically about unit keywords, not all identifiers. I needed to understand exactly what the decision says before I could spot the mismatch.

Entry #3 of 4  |  Date: 2026-05-07  |  Phase: Design  |  Tool: Claude Sonnet 4.6  |  Experiment E1

Goal

[E1] Ask the AI to generate a complete EBNF grammar for Recipix from a one-paragraph description, then compare it to the grammar I designed and identify what it got wrong or suboptimal.

Prompt (verbatim)

"Write a complete EBNF grammar for Recipix, a recipe DSL. The language has: parameterized recipe declarations, scalar helper functions with a return statement, ingredient declarations, step declarations with optional 'at' (temperature) and 'for' (duration) modifiers in fixed order (at before for), let statements, if/else with mandatory braces, repeat...times loops, foreach...in loops, evaluate/scale/substitute top-level operations. quantity_of is a unary operator (not a function). substitute's two ingredient slots must be bare identifiers, not expressions. Comparisons are non-associative. Operator precedence: unary > * / > + - > comparisons > && > ||."

Response (key part — AI-generated grammar excerpt)

<program>      ::= { <top_decl> }
<top_decl>     ::= <recipe_decl> | <function_decl> | <eval_stmt>
<recipe_decl>  ::= "recipe" IDENT "(" [<params>] ")" "serves" <expr> "{" ...
<unary>        ::= "-" <unary> | "!" <unary> | "quantity_of" "(" <expr> ")" | <primary>
<substitute>   ::= "substitute" "(" <expr> "," <expr> "," "with" ":" <expr> "," "ratio" ":" <expr> ")"
<rel_expr>     ::= <add_expr> [ ( "<" | "<=" | ">" | ">=" ) <add_expr> { ( "<" | ... ) <add_expr> } ]

Comparison with my grammar — what the AI got wrong

  • substitute slots wrong: The AI generated <expr> for the ingredient-name slots in substitute. The correct grammar uses IDENT (a terminal), not <expr>. This is exactly Decision #35 — the restriction must be visible in the grammar. The AI missed it despite the explicit instruction.
  • Non-associativity wrong: The AI wrote [ op ... { op ... } ] for relational expressions — the { } still allows chaining. The correct form uses [ op <add_expr> ] only (one optional, not repeating). This would silently permit a < b < c.
  • quantity_of correct: The AI correctly placed "quantity_of" "(" <expr> ")" in the unary production, not in primary. This matched my grammar.
  • Step modifier order not enforced grammatically: The AI wrote [ "at" <expr> ] [ "for" <expr> ] which allows either order. To enforce at-before-for in the grammar, "for" must only appear after the optional "at" block — which requires nested optionals. I accepted this as a grammar limitation and enforced the ordering in the parser (Decision #23) instead.
  • Operator precedence correct: The seven-level hierarchy (unary → mul → add → rel → eq → and → or) matched my grammar exactly.

Accepted

Overall structure (one non-terminal per precedence level), the placement of quantity_of in <unary>, and the basic recipe/function/step shapes. These matched my design.

Rejected / modified

The substitute ingredient-slot production (changed <expr> to IDENT). The relational-expression non-associativity (changed { } to the absent/optional form). These two fixes are exactly the most important design decisions in the language (Decision #35 and #17) — the AI missed both despite them being in the prompt.

Errors caught

Two critical errors: (1) substitute slots as <expr> instead of IDENT — would allow any expression in a position where only symbol-table lookup is allowed. (2) Non-associativity implemented as still-repeating — would allow chained comparisons that should be rejected. Both would have made the grammar accept programs the language spec explicitly forbids.

Reflection

AI handles standard grammar patterns (precedence levels, optional modifiers) well. It fails on design constraints that are local decisions buried in the spec — even when stated in the prompt. The two most domain-specific decisions in Recipix (bare-identifier substitute slots, non-associative comparisons) are exactly the ones the AI got wrong. This confirms that AI-generated grammars need line-by-line verification against the spec, especially at productions that encode non-obvious semantic restrictions.

Entry #4 of 4  |  Date: 2026-05-08  |  Phase: Parser / Integration  |  Tool: Claude Sonnet 4.6

Goal

Integrate the lexer with the partner's parser: identify the token contract differences between the two implementations, fix them without breaking either side.

Prompt (verbatim)

"The lexer and parser were written independently. The lexer's Token class has fields type, value, line. The parser imports Token from recipix/tokens.py and uses getattr(tok, 'col', 0) for column. Both files have their own tokens.py. How do I merge these so there's one source of truth and both the lexer and parser work correctly?"

Response (key part)

Claude identified the problem: two competing Token class definitions. It suggested making src/recipix/tokens.py the single source of truth, updating src/lexer.py to import from recipix.tokens instead of a local tokens.py, and deleting src/tokens.py. It also noted the .col duck-typing pattern in the parser means no changes are needed to the Token class itself.

Accepted

The consolidation strategy (recipix/tokens.py as single source of truth) and the explanation of duck-type compatibility via getattr. Also the sys.path.insert approach in main.py to avoid PYTHONPATH requirements.

Rejected / modified

Claude initially suggested modifying the parser's import path. I rejected this because the parser belongs to my partner and changing it risked introducing bugs in code I had not written. Instead I modified only the lexer's import, which is my component.

Errors caught

Claude suggested python -m recipix as the run command. This failed because the recipix package is inside src/, which is not on the default module path when running from the project root. The fix was a main.py wrapper at the root that adds src/ to sys.path before importing. Claude's suggestion assumed a standard package layout that did not match our structure.

Reflection

Integration problems between separately-written modules are hard for AI to diagnose without seeing both sides simultaneously. Claude's advice was correct in principle but assumed a different project layout. The actual fix required understanding both the Python module system and our specific directory structure — exactly the kind of contextual knowledge that AI does not have by default.
