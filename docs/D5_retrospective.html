What is working

The lexer (src/lexer.py) correctly tokenizes all valid Recipix programs, including the multi-character °C token, two-token quantity literals, boolean literals, and all five keyword categories (reserved, type, action, unit). The Decision #7 enforcement — rejecting 200g while accepting 200foo as a plain integer followed by an identifier — works correctly after a bug fix discovered during integration. The parser (src/recipix/parser.py) parses all three spec sample programs, rejects all five invalid fixture programs with accurate line numbers, and produces a printable AST via --dump-ast. The lexer-parser integration is clean: both modules import token constants from a single source of truth (src/recipix/tokens.py), eliminating the duplicate-token-class bug that appeared early in development. The 48-test suite passes fully.

What is hard

The hardest part of Part 1 was the token contract between the lexer and the parser. The parser was written by my partner and expected a Token class with a .col attribute; our lexer's Token class did not have one. Resolving this required understanding that the parser uses getattr(tok, 'col', 0) defensively, so our tokens are duck-type compatible without any change to either class. This was only clear after reading the parser source carefully — a reminder that interface design needs to be explicit from day one.

A second difficulty was the degree symbol in °C. Windows terminal encoding made the token appear as a question mark in some command-line outputs, which initially looked like a bug in the lexer. The token is stored and compared correctly in memory; the display issue is purely a console encoding artifact.

What to fix in Part 2

  • Type checker architecture. The AST nodes do not yet carry type annotations. For Part 2, every expression node will need an inferred type field so the type checker can propagate dimension information bottom-up and catch mismatches (e.g. flour + water in sample3.rcx).
  • AmbiguousCall resolution. Zero-argument calls are currently parsed as AmbiguousCall nodes because the parser cannot distinguish a recipe from a function by name alone. The Part 2 type checker must resolve these against the name table and replace them with the correct node kind before type-checking proceeds.
  • Scope and single-assignment checks. The parser defers shadowing, re-declaration, and single-assignment violations to Part 2. These need to be implemented in the type checker using a scoped symbol table that tracks each binding's declaration point.
  • Pinch arithmetic guard. The spec says any arithmetic on a Pinch value is a type error (Decision #4). This is not checked anywhere yet and will be the first type rule to implement in Part 2.
