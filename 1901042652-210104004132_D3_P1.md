## 2. Valid example programs

### 2.1 `sample1.rcx` — recipe + helper function

```recipix
function half(n: int) -> int {
    return n / 2
}

recipe pancakes(servings: int) serves servings {
    ingredient flour : 50 g * servings
    ingredient milk  : 60 ml * servings
    ingredient eggs  : half(servings) * 1 count
    ingredient salt  : 1 pinch

    step "Mix dry"     { combine(flour, salt) }
    step "Add wet"     { combine(milk, eggs) }
    step "Cook batches" at 180 °C for 3 min {
        repeat servings times {
            pour(milk)
            flip()
        }
    }
}

evaluate scale(pancakes(servings: 4), by: 1.5)
```

**What it exercises.** A user-defined `function` with `return`, an `int` parameter,
and call from inside a recipe (`half(servings)`); a `recipe` with the `serves <expr>`
clause; four `ingredient` declarations using both arithmetic on quantity literals
(`50 g * servings`) and a function-call result; three `step` blocks including the
domain-specific modifier pair `at 180 °C for 3 min` (Decision #23); the `repeat …
times { … }` loop with action-verb statements (`pour`, `flip`); and a top-level
`evaluate scale(…, by: 1.5)` exercising the `scale` domain construct with a keyword
argument. Decisions #7 (two-token quantity literals), #20 (mandatory braces),
#23 (modifier order) and §11 are all covered.

**CLI output.** `python main.py tests/fixtures/valid/sample1.rcx` →
`OK · parsed tests/fixtures/valid/sample1.rcx`.

### 2.2 `sample2.rcx` — substitution at the call site

```recipix
recipe smoothie(servings: int) serves servings {
    ingredient milk      : 150 ml * servings
    ingredient banana    : 1 count * servings
    ingredient sweetener : 10 g * servings
    ingredient oat_milk  : 150 ml * servings

    step "Blend everything" for 1 min {
        combine(milk, banana, sweetener)
        blend()
    }
}

evaluate substitute(smoothie(servings: 2), milk, with: oat_milk, ratio: 1.0)
evaluate smoothie(servings: 2)
```

**What it exercises.** Our headline domain-specific construct: `substitute(...)` at
the top level, where the original-ingredient and replacement slots are **bare
identifiers** rather than expressions (Decision #35). The keyword arguments
`with:` and `ratio:` exercise the keyword-arg call syntax that distinguishes a
recipe call from a positional function call. The two `evaluate` statements show
that the same recipe can be called with and without substitution from the same
top-level program.

**CLI output.** `python main.py tests/fixtures/valid/sample2.rcx` →
`OK · parsed tests/fixtures/valid/sample2.rcx`.

### 2.3 `sample3.rcx` — well-formed parse with deferred type error

```recipix
recipe broken() serves 1 {
    ingredient flour : 200 g
    ingredient water : 100 ml

    step "Combine wet and dry" {
        // Mass + Volume — caught by the Part 2 type checker, not by the parser.
        let total : Mass = flour + water
    }
}

evaluate broken()
```

**What it exercises.** Demonstrates the boundary between Part 1 and Part 2: the
program is **syntactically well-formed** and the parser accepts it, but adding a
`Mass` to a `Volume` is a dimension-mismatch error our (Part 2) type checker will
reject. Also covers the `let <name> : <Type> = <expr>` form inside a step body
and the implicit ingredient-to-quantity projection that the type system will
later define. Including it in Part 1 lets us assert that the parser is
type-agnostic, as the spec requires.

**CLI output.** `python main.py tests/fixtures/valid/sample3.rcx` →
`OK · parsed tests/fixtures/valid/sample3.rcx`.

## 3. Malformed programs and parser error messages

Each fixture below targets one specific spec decision. The error string is the
verbatim output of `python main.py <file>`; the line number is reported by the
parser.

### 3.1 `missing_brace_if.rcx` — Decision #20 (mandatory braces on `if`)

```recipix
function check(n: int) -> bool {
    if n > 0
        return true
    return false
}
evaluate check(1)
```

**Error (line 6).**
`parse error at line 6, col 0: expected '{' after 'if' condition (braces are mandatory), got 'return' ('return')`

The parser reaches the end of the `if` condition and looks for `{`; finding the
keyword `return` instead, it raises a `ParseError` with the offending line.

### 3.2 `nonassoc_comparison.rcx` — Decision #17 (non-associative comparisons)

```recipix
function between(x: int) -> bool {
    return 0 < x < 10
}
evaluate between(5)
```

**Error (line 5).**
`parse error at line 5, col 0: comparison operators are non-associative; use parentheses to group comparisons (Decision #17)`

After consuming one comparison operator and its right operand, the parser checks
the next token. If it is another comparison operator, it raises this error
rather than silently producing a left-associative parse.

### 3.3 `quantity_of_no_paren.rcx` — Decision #34 (`quantity_of` is a unary operator with parentheses)

```recipix
recipe bread() serves 1 {
    ingredient flour : 200 g
    step "Mix" {
        let q : Mass = quantity_of flour
    }
}
evaluate bread()
```

**Error (line 8).**
`parse error at line 8, col 0: expected '(' after 'quantity_of', got 'IDENT' ('flour')`

Decision #34 makes `quantity_of` a unary operator that requires parentheses
around its operand (`quantity_of(flour)`). Omitting them is a parse error,
not a runtime or type error.

### 3.4 `substitute_expr_slot.rcx` — Decision #35 (substitute slots are bare identifiers)

```recipix
evaluate substitute(smoothie(servings: 2), milk + oat_milk,
                    with: oat_milk, ratio: 1.0)
```

**Error (line 13).**
`parse error at line 13, col 0: substitute: original ingredient must be a bare identifier — expressions are not allowed here (Decision #35 / error #17); got 'PLUS' after identifier 'milk'`

Decision #35 commits the substitute slots to identifier syntax (so the
`SubstituteCall` AST node stores `original_name: str`, not `Expr`). The parser
detects an arithmetic operator after the identifier and rejects the program.

### 3.5 `wrong_modifier_order.rcx` — Decision #23 (`at` before `for` in step modifiers)

```recipix
step "Bake" for 30 min at 180 °C {
    bake(flour)
}
```

**Error (line 7).**
`parse error at line 7, col 0: 'at' modifier must come before 'for' modifier in step declaration (Decision #23)`

The parser consumes step modifiers in fixed order: `at` (temperature) first,
then `for` (duration). Encountering `at` after `for` raises this error pinned to
the spec decision number.
